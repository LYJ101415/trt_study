# 改动分析：Resize 移到 CPU，GPU kernel 只做归一化 + 转通道

## 1. 改了什么

| 阶段 | 改动前 | 改动后 |
|------|--------|--------|
| 预处理 Resize/letterbox | GPU `letterbox_preprocess_kernel`（逐像素双线性插值 + 灰色 pad） | **CPU `cv2.resize` + 灰色 pad**（读取图片时做，见 `common.letterbox_cpu`） |
| 预处理 归一化/转通道 | 同上，一个融合 kernel 一起做 | **GPU `normalize_transpose_kernel`**（只做 BGR→RGB + ÷255 + HWC→CHW） |
| H2D 传输量 | 整幅原图（H×W×3） | 固定 640×640×3 ≈ 1.2 MB |
| 后处理 decode + NMS | GPU 不变 | GPU 不变（仍需 scale/pad 反 letterbox） |
| 模型 | （旧路径指向不存在的 engine） | `/root/my_FILE/models/yolov8_int8_static.engine` |

核心代码变化：

- `kernels/gpu_ops.cu`：`letterbox_preprocess_kernel` → `normalize_transpose_kernel`（每个线程 3 读 3 写，
  无插值、无 pad 分支）；`gpu_letterbox` → `gpu_preprocess`，签名从 8 个参数简化为 4 个。
  顺带修复了 NMS kernel 里 3 处 `float yy1/yy2/ih` 漏写类型导致无法编译的历史 bug。
- `dependency_file/common.py`：新增 `letterbox_cpu()`，并把原 `preprocess_cpu()` 重构为复用它。
- `server_gpu.py` / `eval_kernel_map.py`：infer 流程改为「CPU letterbox → H2D 640×640 → GPU 归一化转通道 →
  execute_v2 → GPU 后处理」，engine 路径与数据集路径改为实际存在的路径，并修复了 import 路径。
- `kernels/compile.sh`：修复 nvcc 路径（`/usr/local/cuda-12.4`）。

## 2. 这个改动是否更好？

**结论：对「输入 > 640×640」的场景更好；对「输入已经是 640×640」的场景基本打平、略偏负。**

实测（RTX 4080，200 次取平均，逐段同步）：

| 阶段 | 640×640 输入 | 说明 |
|------|-------------|------|
| CPU letterbox（cv2.resize + pad） | 0.338 ms | 新增的 CPU 开销 |
| H2D 640×640×3 | 0.179 ms | 同步 `cudaMemcpy` |
| GPU 归一化 + 转通道 | 0.017 ms | 原 letterbox kernel 会做插值，更贵一些 |
| TRT execute_v2 (INT8) | 0.575 ms | 不变 |
| GPU 后处理（decode + NMS） | 0.147 ms | 不变 |

**变好的地方：**

1. **H2D 数据量大幅下降**（核心收益）。本数据集 640×640 时 H2D 都是 1.2 MB；一旦输入是 1920×1080，
   旧方案要传 6.2 MB，4K 要传 ~50 MB，新方案永远只传 1.2 MB（5~40× 减少）。PCIe H2D 带宽是常见瓶颈，
   这一步对大图是实打实的收益。
2. **GPU kernel 更轻**：从「逐像素双线性插值（4 邻居 × 3 通道）」简化为「逐像素 3 读 3 写」，
   GPU 预处理从 ~几十 μs 降到 ~17 μs，几乎可忽略。
3. **CPU resize 是 SIMD 优化实现**，且 CPU 上的 resize 与 GPU 推理天然具备「错位并行」的潜力
   （见第 3 节）——为后续多帧流水线打基础。

**变差 / 持平的地方：**

1. 本数据集 500 张图**全是 640×640**，此时 letterbox 的 scale=1.0、pad=0，`cv2.resize(640→640)` 是
   「冗余的一次全图拷贝」+ 新建 canvas 又一次拷贝，白白多了 ~0.34 ms 的 CPU 串行开销；
   而旧方案 GPU 插值 kernel 也很快（几十 μs 量级），所以对本数据集是**打平或略负**。
2. CPU 端多了一次 1.2 MB 的 canvas 分配（`np.full`）。若追求极致，可复用预分配 canvas 缓冲、
   且 scale==1 时跳过 resize。

**一句话总结**：把 Resize 放到 CPU 是一个「用 CPU 的 SIMD 算力 + 更小的 H2D 换 GPU 算力」的取舍。
生产环境输入分辨率通常大于模型输入 640，此时**明显更好**；在「输入已经等于模型尺寸」的测试集上，
收益消失、反而多了一点 CPU 拷贝，属于**中性偏负**。

## 3. GPU 上预处理 / 推理 / 后处理是否异步并行？

**结论：没有。当前三者严格串行，且存在多处 host 侧同步点。**

证据（从代码看执行模型）：

1. **全部跑在默认流（legacy default stream = 0）上**：`gpu_preprocess`、`execute_v2`、
   `gpu_postprocess` 都传 `stream=0`。legacy default stream 会与所有其它流隐式同步，
   天然把这三个 kernel 串行化。
2. **H2D 是同步拷贝**：`common.cuda_memcpy_h2d` 调的是 `cudaMemcpy`（不是 `cudaMemcpyAsync`），
   拷贝完成前 host 被阻塞，也强制与默认流串行。
3. **后处理里有两次 `cudaStreamSynchronize`**：`gpu_postprocess` 为了拿到候选数 n、最终框数 n，
   主动把 host 卡在 GPU 上等两次。
4. 单帧内这三步本就有数据依赖（推理依赖预处理输出、后处理依赖推理输出），**单帧内无法并行**；
   能做的并行是**跨帧流水线**（帧 N+1 的预处理与帧 N 的推理重叠），但当前单线程 `infer()` + 默认流
   完全没有这种重叠。

要真正做到异步并行，需要：

1. 用**非默认流**（每帧一个 stream），让相邻帧的 preprocess / inference / postprocess 错位重叠；
2. 用 **pinned host memory + `cudaMemcpyAsync`** 让 H2D 与计算重叠；
3. 用**生产者/消费者双线程**：CPU 线程做 imread + letterbox（本次改动把 resize 移到 CPU 后，
   CPU 与 GPU 正好可以错峰并行），GPU 线程消费。

本次改动**本身没有引入**异步并行（甚至让 CPU 侧多了串行 resize），但它是实现「CPU 预处理与 GPU
推理错位并行」的前提——因为 resize 现在在 CPU 上，才可能和上一帧的 GPU 推理同时进行。

## 4. 测试结果

- **正确性**：GPU 归一化+转通道 与 CPU 参考 `preprocess_cpu` 逐元素对齐，max diff = 5.96e-8（float 舍入级）。
- **端到端**：`python server_gpu.py` 单图 5 目标正常检出，单帧 1.8 ms。
- **COCO mAP**（`yolov8_int8_static.engine`，500 张 test，conf=0.001 / iou=0.65）：

| 指标 | 数值 |
|------|------|
| mAP@[0.50:0.95] | **0.7492** |
| mAP@0.50 | **0.9564** |
| mAP@0.75 | **0.8989** |

mAP 与参考管线一致，证明「Resize 移 CPU」未改变检测语义。

## 5. 运行方式

```bash
# 编译 kernel（已在 kernels/ 下生成 libgpu_ops.so）
bash kernels/compile.sh

# 逐段耗时测试（CPU letterbox / H2D / GPU 归一化 / TRT / 后处理）
python profile_stages.py

# 单图 / 批量推理
python server_gpu.py /root/autodl-tmp/datasets/Data_DeepPCB_YOLO/images/test/00041200.jpg

# COCO mAP 评测
python eval_kernel_map.py \
  --engine /root/my_FILE/models/yolov8_int8_static.engine \

```
