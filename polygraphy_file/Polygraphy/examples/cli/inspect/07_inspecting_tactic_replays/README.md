# Inspecting Tactic Replay Files


## Introduction

The `inspect tactics` subtool can display information about TensorRT tactic replay
files generated by Polygraphy.


## Running The Example

1. Generate a tactic replay file:

    ```bash
    polygraphy run model.onnx --trt --save-tactics replay.json
    ```

2. Inspect the tactic replay:

    ```bash
    polygraphy inspect tactics replay.json
    ```

    This will display something like:

    ```
    [I] Layer: ONNXTRT_Broadcast
            Algorithm: (Implementation: 2147483661, Tactic: 0) | Inputs: (('DataType.FLOAT'),) | Outputs: (('DataType.FLOAT'),)
        Layer: node_of_z
            Algorithm: (Implementation: 2147483651, Tactic: 1) | Inputs: (('DataType.FLOAT'), ('DataType.FLOAT')) | Outputs: (('DataType.FLOAT'),)
    ```
=========================================================================
这份文档介绍了 如何使用 Polygraphy 的 inspect tactics 工具来分析 TensorRT 的“战术回放文件”（Tactic Replay File）。这是深入理解 TensorRT 优化决策、复现构建行为、调试性能问题的高级功能。

下面从 核心概念、技术原理、命令流程、输出解析、工程价值、高级用法 六个维度进行深度解析。

一、核心概念：什么是 Tactic Replay？
1. 背景：TensorRT 的“战术选择”机制;TensorRT 在构建引擎时，对每个层（Layer）会尝试 多种实现方式（Implementation）和算法（Tactic）,例如：卷积可用 cuDNN、CUTLASS、自定义 kernel 等,每种实现下又有多个 tactic ID（代表具体配置，如 tile size、shared memory 使用）,通过 Profiling 选择最快的一种
2. 问题：构建结果不稳定;同一模型在不同机器/驱动/CUDA 版本下，可能选择 不同的 tactic
导致：性能波动;精度微小差异（某些 tactic 有数值误差）;无法复现“最优”构建结果
3. 解决方案：Tactic Replay;记录 构建过程中每个层选择的 (Implementation, Tactic) 对
回放 该记录，强制 TensorRT 使用相同 tactic;实现 确定性构建（Deterministic Build）

 Polygraphy 的 --save-tactics 就是生成这种记录文件
二、技术原理：Polygraphy 如何捕获 Tactics？
内部机制：创建自定义 IAlgorithmSelector,这是 TensorRT 提供的回调接口，用于干预 tactic 选择;在构建时拦截所有层的选择结果;记录：层名、Implementation、Tactic、输入/输出数据类型;序列化为 JSON 文件（replay.json）
关键点：不修改原始模型，仅记录选择结果。
回放时：通过 --load-tactics 注入相同的 IAlgorithmSelector
三、命令流程详解
步骤 1：生成战术回放文件
polygraphy run model.onnx --trt --save-tactics replay.json
--trt：使用 TensorRT 后端
--save-tactics：启用 tactic 捕获并保存到 replay.json
 注意：此过程会完整构建一次 TRT 引擎（耗时）

步骤 2：检查战术内容
polygraphy inspect tactics replay.json
解析 JSON 并格式化输出人类可读的战术信息
四、输出结构深度解析：示例输出：
[I] Layer: ONNXTRT_Broadcast
        Algorithm: (Implementation: 2147483661, Tactic: 0) | Inputs: (('DataType.FLOAT'),) | Outputs: (('DataType.FLOAT'),)
    Layer: node_of_z
        Algorithm: (Implementation: 2147483651, Tactic: 1) | Inputs: (('DataType.FLOAT'), ('DataType.FLOAT')) | Outputs: (('DataType.FLOAT'),)
逐字段解读：
1. 层标识（Layer Name）
Layer: ONNXTRT_Broadcast
来源：若 ONNX 节点有名字 → 使用该名字，否则由 TensorRT 自动生成（如 ONNXTRT_Broadcast 表示广播操作）
2. 算法选择（Algorithm）
(Implementation: 2147483661, Tactic: 0)
Implementation：32 位整数，高 16 位 = 库 ID，低 16 位 = 算子 ID；
例如 2147483661 = 0x8000000D → 库 ID=0x8000（cuDNN），算子 ID=0xD
Tactic：具体算法配置的枚举值（无公开文档，由 TRT 内部定义）
相同 Implementation 下，不同 Tactic 代表不同优化策略
 关键洞察：这些数字本身无直接语义，但组合 (Impl, Tactic) 唯一确定一个 kernel
3. 输入/输出数据类型
Inputs: (('DataType.FLOAT'), ('DataType.FLOAT'))
Outputs: (('DataType.FLOAT'),)
显示该层的 输入/输出张量的数据类型，用于确保回放时类型匹配（否则 tactic 可能无效）
五、工程价值：为什么需要 Inspect Tactics？
场景 1：性能回归分析
发现新版本 TRT 性能下降；对比新旧 replay.json：
polygraphy inspect tactics old_replay.json > old.txt
polygraphy inspect tactics new_replay.json > new.txt
diff old.txt new.txt
定位是哪个层的 tactic 发生了变化
场景 2：跨平台一致性保证；在 A 机器上找到最优 tactic；将 replay.json 复制到 B 机器
使用 --load-tactics replay.json 强制相同选择；确保性能/精度一致
场景 3：调试精度问题；某个 tactic 导致 NaN；通过 inspect 定位问题层；
在回放时排除该 tactic（需自定义 selector）
场景 4：学术研究/内核分析；分析 TRT 对特定算子（如 GroupConv）的优化策略；统计常用 tactic 分布
六、高级用法与技巧
1. 回放战术（核心用途）
# 使用记录的 tactic 重新构建
polygraphy run model.onnx --trt --load-tactics replay.json --save-engine model.plan
2. 结合 Profiling 分析
# 生成带 tactic 的 engine 并 profiling
polygraphy run model.onnx --trt --load-tactics replay.json --profile
验证回放后性能是否与原始一致
3. 自定义战术过滤
虽然 Polygraphy 不直接支持，但可通过 API 实现：
from polygraphy.backend.trt import TacticReplayData

replay = TacticReplayData.load("replay.json")
# 修改某层的 tactic
replay["problematic_layer"] = (impl, new_tactic)
replay.save("fixed_replay.json")
4. 可视化战术依赖
某些 tactic 依赖特定 CUDA 架构，通过 inspect 输出 + TRT 日志，可反推硬件要求
七、注意事项与局限性
限制	          说明
TRT 版本敏感	tactic ID 在不同 TRT 版本中可能变化
硬件依赖	    某些 tactic 仅在特定 GPU 架构有效
不保证存在	     回放时若 tactic 不可用，TRT 会 fallback 到其他选择
无语义解释	    Implementation/Tactic 是黑盒数字，NVIDIA 未公开含义
仅适用于显式tactic 层	某些融合层（如 CBR）可能不单独记录

 总结：inspect tactics 的核心价值
维度	    说明
定位	    TensorRT 优化决策的“黑匣子记录仪”
核心作用	实现 可复现、可分析、可控制 的引擎构建
典型用户	高级部署工程师、性能调优专家、TRT 插件开发者
不可替代性	是解决“为什么这次构建变慢了？”的终极工具

 一句话精髓：“Tactic Replay 让 TensorRT 的随机优化变成确定性工程。”而 inspect tactics 就是解读这个确定性记录的钥匙。因此，尽管这是一个高级功能，但在追求极致性能稳定性和可复现性的生产环境中，它往往是不可或缺的利器。
